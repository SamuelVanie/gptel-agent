#+title: gptel-agent

This is a collection of tools and prompts to use [[https://github.com/karthink/gptel][gptel]] "agentically" with any
LLM, to autonomously perform tasks.

It has access to
- the web (via basic web search and URL fetching, including YouTube video
  descriptions and transcripts),
- local files (read/write/edit),
- the state of Emacs (documentation and Elisp evaluation),
- and Bash, if you are in a POSIX-y environment.

By default, all actions except for web search, fetching URLs and reading local
files require confirmation.  You can change this, add more tools and MCP servers
etc as in regular gptel usage.

gptel-agent can also delegate tasks to specialized "sub-agents" which don't
share context with the main session.  In this demo, gptel-agent delegates a
research task to two different sub-agents, who perform it in parallel and
generate reports that gptel-agent uses to answer the question:

https://github.com/user-attachments/assets/03585600-3bb9-4bf7-b5c8-7e02a28c7a37

*** How to use:

- Important: ensure that gptel is up to date, and not just the latest stable release!

- Set =gptel-model= and =gptel-backend= to use your preferred LLM.  See [[https://github.com/karthink/gptel][gptel's
  README]] for details.

There are two ways to use gptel-agent:

**** In a dedicated session

- Run M-x =gptel-agent=.  This will open a gptel buffer in the current project
  with the agent preset loaded.  Run with a prefix arg for more options.

- Use gptel as usual, calling =gptel-send= etc.

- If you change the system prompt, tools or other settings in this buffer, you
  can reset the agent configuration by (re)applying the "gptel-agent" preset
  from gptel's menu.

- You can switch between an agent preset (gptel-agent) and a planning preset
  (gptel-plan) by applying them from gptel's menu, or clicking on the backend
  name in the header line.

  The difference between them is just in the tools available to the model -- the
  planning preset has read-only access to the filesystem and is instructed to
  create a systematic plan of action.

**** Anywhere in Emacs

Place =(gptel-agent-update)= in your config.

As with gptel, you can use gptel-agent in any buffer, including read-only
buffers and the minibuffer.

- Apply the "gptel-agent" preset in the buffer from gptel's menu.

- OR include =@gptel-agent= in a prompt to send only that prompt with the agent
  capabilities.

Please note: gptel-agent uses significantly more tokens than the average
gptel LLM interaction.

*** Working directories

Use =M-x cd= in a chat buffer to change its working directory. Subsequent
tools and requests use the new directory; project-instruction discovery
refreshes automatically, including when moving to a different project. The
conversation history remains available. Other chats and already running
workers or shell processes keep their own directories.

Both =Agent= and =Discussion= accept an optional =directory= argument, for
example ="/path/to/project"= or ="../other-project"=. The directory must exist;
relative paths resolve against the calling chat's directory. Each child
discovers project instructions in its own directory. Omitting =directory=
inherits the parent's directory for a new child. An =Agent= follow-up using
=agent_id= keeps the worker's current directory unless =directory= is supplied.

Agents can request a move with =ChangeDirectory(directory, reason)=, for example
=ChangeDirectory("../other-project", "Read the shared API implementation")=.
The approval shows the agent/chat, current directory, absolute destination and
reason. Use the normal tool approval controls (=C-c C-c= to approve,
=C-c C-k= to cancel). This tool always requires approval, even with ordinary
tool confirmations disabled or skill pre-approvals enabled. Cancelling leaves
the directory unchanged. The destination must already exist and be local.

Call =ChangeDirectory= alone; a batch combining it with other tools is deferred
without running any of them. After approval, the next model call receives the
new project's instructions before the agent retries its read or write. To move
back, request another change. A stale approval after cancellation, a manual
directory change, or a destination change cannot move the agent.

A =cd= inside =Bash= affects only that shell invocation. =ChangeDirectory= is
an approval workflow for moving the conversation, not an operating-system
sandbox for arbitrary shell commands or Elisp evaluation.

*** Scoped project instructions

All gptel conversations automatically discover plain-text =AGENTS.md= files
while =gptel-agent-use-project-instructions= is non-nil, regardless of preset
or agent identity. The first outgoing request includes these instructions even
with =Read= or all tools disabled. Discovery starts at the conversation's
project root and follows the directory chain to its working directory. Without
an Emacs project, the working directory is the boundary. File context and
=Read=, =Glob=, =Grep=, =PathInfo=, =Edit=, =Insert=, =Write=, =Mkdir= and =Rmdir= targets discover deeper
chains as needed; the project is never scanned recursively.

For example, work on =frontend/view.ts= receives the root =AGENTS.md= followed
by =frontend/AGENTS.md=. Work on =backend/server.ts= receives the root and
backend instructions instead. A request targeting both receives both scoped
chains, with common ancestors included once. More specific instructions take
precedence over conflicting parent rules; explicit user instructions take
precedence over project rules.

Each conversation owns its discovered contents and request snapshots. New
workers and managed discussions independently discover their own instructions;
they do not inherit the parent's loaded contents. Continuing a worker retains
its private registry. Instruction blocks are rebuilt before every outgoing
call, including retries and tool continuations, without changing the configured
system prompt, preset or conversation text. Compaction keeps the private registry
and subsequent requests rebuild from it. Closing the conversation discards its
registry; reopened conversations rediscover their instructions.

Managed =Read= calls for =AGENTS.md= return a short acknowledgement, even when
a line range was requested. The contents travel through the replaceable
instruction block instead of accumulating in tool-result history. Use
=M-x gptel-agent-describe-project-instructions= to inspect the full local
contents, discovery boundary, discovered sources and latest delivered block.
Explicit quotations, attached task data and arbitrary command output remain
ordinary conversation data.

Before a file mutation, the harness checks all applicable saved instruction
versions against the ones supplied to the model. A missing or changed scope
defers the operation before staging or writing. The next call receives updated
instructions and asks the model to reconsider and propose a fresh operation.
Old arguments are never replayed automatically. Batches discover every target
before any edit is staged, including multi-file patches. Saved changes,
additions and deletions are refreshed at new turns and checked before mutations.
Delayed tool approvals are checked again when executed.

Use =M-x gptel-agent-toggle-project-instructions= to toggle just the current
conversation. A positive prefix enables it; zero or a negative prefix disables
it. Changes take effect at the next outgoing call. Other conversations and
already submitted snapshots are unaffected. The global variable supplies the
default for every conversation; buffer-local values override that default.

#+begin_src emacs-lisp
;; Disable globally for conversations without a local override.
(setq-default gptel-agent-use-project-instructions nil)

;; Enable only this conversation, overriding the global default.
(setq-local gptel-agent-use-project-instructions t)

;; Disable only this conversation.
(setq-local gptel-agent-use-project-instructions nil)
#+end_src

Internal workers restricted to a single result file do not perform project
instruction discovery, even when their parent enables it.
New workers and discussions inherit the effective boolean preference only.

Managed file operations support local files within the conversation's current
discovery boundary. File/directory symlinks inside that boundary resolve to their
canonical target scopes. Escaping symlinks, remote targets, and targets outside
the boundary report an error before ordinary managed file operations. Use
=ChangeDirectory= to request permission to move into the target project, or
change the chat directory yourself with =M-x cd=.

=AGENTS.md= may be a symlink to a readable regular local file, including a
shared file outside the project. Absolute and relative links are supported.
The source and scope remain the project's =AGENTS.md= path and its containing
directory, so a link at the project root applies to that project and a nested
link applies only to its subtree. The shared target's directory does not become
an instruction scope or expand access for ordinary file operations. Managed
=Read= calls and attached context using the project's =AGENTS.md= path retain
this local scope.

For example, to share one rules file between two projects that do not already
have an =AGENTS.md=:

#+begin_src sh
ln -s "$HOME/shared-rules/AGENTS.md" /path/to/project-a/AGENTS.md
ln -s "$HOME/shared-rules/AGENTS.md" /path/to/project-b/AGENTS.md
#+end_src

Saved changes to the shared file and changes to the symlink target are refreshed
by the normal instruction checks. Broken or cyclic links, unreadable or non-file
targets, remote targets, and files exceeding
=gptel-agent-project-instructions-max-bytes= (128 KiB by default) produce visible
diagnostics and block mutations in their scopes; stale or truncated contents are
not silently used.

The per-call payload adapter covers OpenAI Chat Completions and compatible
=:messages= backends, OpenAI Responses, Anthropic, Gemini, and Ollama. It preserves
ordinary messages and tool-call/result pairs. Provider-side conversation handles
or =previous_response_id=, and Gemini =cachedContent=, are rejected when adding
or removing managed instructions:
requests must carry their full context so old blocks cannot remain implicitly
active. Models without system-message support are also rejected when a managed
block is needed.

This feature controls the instruction text supplied to the model, not semantic
compliance with that text. It cannot infer every effect of arbitrary =Bash= or
=Eval= code, erase previous reasoning, or enforce natural-language rules.
Prefer the file tools for work requiring deterministic scope checks.

*** Asking questions while working

=AskUserQuestion= accumulates questions across tool calls. Its default
=action: "add"= returns immediately, so the agent can continue independent
work and add further questions. When the list is ready, it calls
=action: "wait"= with =questions= omitted or empty. That call pauses the
turn and returns the complete answers (or a cancellation). If the model tries
to finish with an uncollected question batch, the runtime automatically waits
for it instead. The turn stays open, submission becomes available, and the
same request resumes with the answers or cancellation before it can finish.

Questions appear in a separate =*Questions: …*= buffer that refreshes in
place as the list grows. Existing answers, choices and custom text are
preserved. By default, it opens below the conversation window, without taking
focus. It only splits that window, leaving other windows alone. If the window
is too short to split, questions temporarily replace the conversation there.
Set =gptel-agent-questions-display= to =same-window= to always use that behavior;
submitting or cancelling restores the conversation. Its default value is
=below=.

If the conversation is hidden, questions stay queued without changing the
layout. Use =M-x gptel-agent-questions= from the conversation to show them,
including questions from its workers. Each request has its own queue.

| Key | Action |
|-----+--------|
| =1-9=, =n/p=, =TAB= | Select a choice |
| =RET= | Save the answer and move to the next question |
| =M-p/M-n= or =←/→= | Revisit questions and revise answers |
| =C-c C-c= | Submit all answers once the agent is waiting |
| =C-c C-k= | Cancel the question batch |
| =q= | Hide the buffer |

You can save answers while the agent is working; submission becomes available
when it calls =wait= or the runtime catches an early completion. Every question
also has a free-text Custom option.
Cancelling or killing the questions buffer records a cancellation for =wait=;
it never supplies default answers. An early completion also delivers any
uncollected cancellation to the model. Aborting, failing or closing the owning
request removes its queue and invalidates late answers. A subsequent batch
starts fresh after its result is collected. In managed discussions, the
completed list becomes a pending interaction for =DiscussionControl answer=
when an explicit or automatic wait starts.

*** Reviewing file edits with Ediff

Loading =gptel-agent= (or =gptel-agent-tools=) automatically enables Ediff
review for =Edit=, =Insert= and =Write= when =gptel-confirm-tool-calls= is
non-nil.  No separate prehook configuration is needed.  After updating an
existing installation, rebuild the package and restart Emacs so the new
libraries and hook are loaded.  Remove any explicit load of an older custom
prehook to avoid overriding the bundled implementation.

File proposals now collect in a separate =*File review: …*= buffer. The tool
returns immediately, so the agent can continue proposing modifications while
you review. Open the queue again with =M-x gptel-agent-review= from the
conversation buffer. Each file has one cumulative diff: its original content
on the left, its latest proposed content on the right. Later proposals for that
file, including writes, insertions and deletions, update the same entry and
open Ediff in place. The list shows each file's revision and decision.
Sub-agent changes join their parent conversation's queue. Different
conversations have separate queues; a file under review cannot be claimed by
another conversation until its review is finished.

In the review queue:

| Key | Action |
|-----+--------|
| =RET= | Inspect the selected file's cumulative diff in Ediff |
| =H= | Send a comment on this file immediately |
| =A= | Ask about this file in an independent aside chat |
| =r= | Restore this file's original contents and send optional feedback |
| =a= | Explicitly accept all current file revisions |
| =D= | Finish review quietly once every file has a decision |
| =C= | Restore all original contents and notify the agent immediately |
| =g= | Refresh the list |
| =q= | Hide the queue; changes remain pending |

In the Ediff control buffer:

| Key | Action |
|-----+--------|
| =n= / =p= | Next / previous change in this file |
| =N= / =P= | Next / previous file, keeping the current change position |
| =f= | Choose a file by path |
| =q= | Accept this file's displayed revision and return to the list |
| =Q= | Hide Ediff without making a decision |
| =R= | Restore this file's original contents and send feedback immediately |
| =C= | Cancel the entire queue and finish review |
| =H= | Send a comment; in A/B include the selected region or current line |
| =A= | Ask in an aside; in A/B include the selected region or current line |
| =C-]= | Refuse this file and close its Ediff |

The Ediff headers show your position in the queue, such as =File 2 of 5=.
When =N= wraps from the last file to the first, a highlighted
=Wrapped to first file= notice stays until you open another file. =P= similarly
announces wrapping to the last file. The file count updates as proposals arrive;
moving between files does not accept them.

=A= opens a =*Review aside: …*= chat below Ediff. Asking leaves the proposal's
decision unchanged, so you can still accept it immediately. The aside starts
with a snapshot of the conversation's history, model, system prompt and request
settings, plus the original/proposed file contents and the displayed revision.
It includes the usual attached context and scoped project instructions. Its
tools are disabled: questions request explanations, not edits. Questions and
answers stay in the aside and are never added to the original conversation.

Each file has its own aside. Ask further questions with =A=, or type directly
in the aside and send with =C-c RET=. To discuss a specific passage, mark it
in either diff pane and press =A= there, just like =H= for a comment. The
aside keeps the exact selection, its line range and the displayed revision.
With no region, it uses the current line. Review keys take precedence over
modal editing bindings (such as Meow's =A=) in these temporary review buffers.
An empty answer to the =A= prompt reopens the aside without sending.
=C-c C-r= returns to the file's Ediff, =C-c C-q= hides the aside, and =C-c C-k=
cancels only its current answer. Closing Ediff or finishing review keeps the
aside available as a normal buffer. Killing the aside cancels its request
without affecting the original agent. The inherited
conversation history is a snapshot; asking again with =A= includes the file
revision you are then viewing.

By default, proposals are applied to working files immediately, with before/after
copies saved before writing. Bash commands, tests, builds, =Read=, =Grep= and
=Glob= can therefore use the proposed changes while you review. The agent is
instructed to run relevant checks, fix failures and report the results before
finishing. Bash keeps its normal tool confirmation behavior.

If a formatter, Bash command, or another program changes a file already under
review, its saved contents become the next revision of that same cumulative
diff. Further agent edits build on those contents, preserving the command's
effects. The pre-review original stays fixed, and the external before/after
transition is saved in history. Files that include external changes are marked
in the review list and Ediff header.

Synchronization runs after =Bash=/=Process= tool results, on =Read= and further
file edits, and when opening, refreshing (=g=), or deciding a review. Unmodified
visiting Emacs buffers refresh too. Unsaved buffer edits are never discarded;
save or reconcile them before continuing. Changes made outside the agent are
picked up at the next such operation; this is not a filesystem watcher.

=D= requires a decision on every current file revision; use =RET= to inspect
pending files, or explicitly accept them all with =a=. A new change to an
accepted file makes it pending again. Open comparisons refresh without
rebuilding their windows or taking focus. Accepting everything closes review
without appending a summary prompt or starting another agent response.
If an accept, refuse, or finish command discovers external changes, it refreshes
the diff and leaves the decision pending. Inspect the updated revision and
repeat the command.

Comments and refusals are submitted immediately, without waiting for =D=.
An active agent receives feedback at the next completed tool boundary, before
its next model request. If its response ends without another tool call, the
feedback starts a follow-up response. Aborting or failing a request cancels
feedback already waiting on it; a new comment/refusal afterward still sends
automatically. Active sub-agent authors also receive feedback
in their next tool result. Comments retain the displayed revision, filename,
line range and selected text, even if changes arrive while you type.

A comment leaves the proposed content available for the agent to revise. =q=
waits for a revision on a file with feedback; =Q= lets you leave its Ediff.
Refusing a file restores its pre-review contents, including removing newly
created files or recreating deleted ones. This also undoes formatter or other
external changes included in that file's diff. Other files keep their changes.
An adjusted proposal for the refused file starts from disk in the same list
entry. Feedback is sent automatically; there is no draft to edit and submit.
Restoration checks the whole batch before writing and refuses to overwrite
unsaved buffers or changes arriving during preparation. The restored version
is also saved in history, so a refusal can itself be undone.

Preview buffers are read-only. If manually altered, they cannot be accepted;
close with =Q= and reopen the file to restore the staged comparison.

To retain the previous staging workflow, set
=(setq gptel-agent-review-apply-immediately nil)= before starting a new review.
In that mode only file tools and =Read= see proposals until =D= applies them;
Bash, tests, =Grep= and =Glob= see the old disk contents. Tool results state
whether changes are applied or only staged. Changing this setting or turning
confirmation off during a review does not change that queue's behavior.
With confirmation nil and no pending queue, file tools apply directly and
still save history snapshots.

Use =M-x gptel-agent-history= to browse saved batches, =RET= to inspect a file's
diff, and =r= to undo the selected batch's visible files. =M-x gptel-agent-history-restore=
also lets you choose a snapshot directly. Finish any active review for those
files first. Restores require files to match that snapshot's after-state;
restore newer changes first to step back through history. Each restore is
itself saved, so it can be undone. Originals, proposed versions, encoding and
file permissions are recorded, including creation and deletion of empty files.

Cancelled changes and the entries that cancelled them are hidden by default.
Press =c= to show or hide them. The Status column marks =[-] Cancelled=,
=[x] Cancellation=, and =[+] Recovery=; batch IDs and the Related batches column
link each cancellation to its original changes. Review refusals include all
revisions of the refused file, including observed external edits. A partially
cancelled batch stays visible as =[~] Partly cancelled=, showing only its remaining
files by default; =RET= and =r= act on the files shown by the current filter.
To recover cancelled changes, press =c= and undo their cancellation entry.
The original changes then reappear in the default view. Recovery entries are
also kept in the expanded view. Older snapshots without cancellation links
remain visible because their review decisions cannot be determined reliably.

Press =d= to permanently delete the selected batch from history, or use
=M-x gptel-agent-history-delete= to choose one directly. After confirmation,
the saved snapshots are removed without changing working files. Cancellation
and recovery links are followed in both directions: all connected batches
are deleted together, including revisions or files sharing a cancellation.
Deletion covers whole batches, including files hidden by the current filter;
the confirmation reports the total number of batches to remove.

Snapshots live under =gptel-agent-history-directory=, by default a private
=gptel-agent-history-UID/= directory in the system temporary folder. They
survive closing conversations and restarting Emacs, but the operating system
may clean temporary files. Set this variable to a permanent directory for
long-term retention. Closing a conversation leaves applied changes on disk;
use history to restore them later. History covers changes through file tools
and external changes observed in files already under review. It does not track
other files changed by Bash commands or external programs, or intermediate
versions overwritten between synchronization points.

=Edit= accepts string replacements, unified diffs, or an =operations= array
with =path= set to an existing root directory. Operations can mix =replace=,
=patch=, =insert=, =write= (create or overwrite), and =delete=. Each operation
has an =operation= name and a =path= relative to the root, plus the fields it
needs: =old_str=/=new_str= for replacement, =new_str= for a patch,
=line_number=/=new_str= for insertion, or =content= for writing. Operations
run in order, with one original/final comparison per affected file in the
review. Unified diffs can also create/delete files using =/dev/null=.
Renames, binary files and mode changes remain unsupported. Shell/Elisp side
effects are not intercepted; use the structured tools for reviewable changes.

Select exactly one =Edit= mode:

- Replacement: file =path=, nonempty =old_str=, literal =new_str= (empty
  deletes the matched text), and =diff=false=.
- Unified diff: file or directory =path=, =diff=true=, and the patch in
  =new_str=. Omit =old_str= or set it to an empty string.
- Batch: directory =path= and a nonempty =operations= array. Omit top-level
  =old_str=, =new_str= and =diff=, or set them to =""=, =""= and =false=.

For replacement or unified diff, omit =operations= or use =[]=. Never add
dummy operations to fill an unused array. Nonempty operations combined with
top-level replacement text or =diff=true= are rejected before changing files.
Unused fields within an operation may be omitted; if the model supplies every
field, use empty strings and =line_number=0= for unused fields.

These examples include every top-level parameter:

#+begin_src json
{"path":"/project/a.txt","old_str":"old","new_str":"new","diff":false,"operations":[]}
#+end_src

#+begin_src json
{
  "path": "/project",
  "old_str": "",
  "new_str": "",
  "diff": false,
  "operations": [
    {"operation":"replace","path":"a.txt","old_str":"old","new_str":"new"},
    {"operation":"write","path":"b.txt","content":"created\n"}
  ]
}
#+end_src

Preparation and execution share =gptel-agent-edit.el=. Failed patches,
ambiguous replacements and no-op edits report an error without altering the
queue or target files. Replacements try exact matching first, then a unique
match of complete lines ignoring indentation and trailing whitespace, aligning
the new block's indentation with the source. Case, words, punctuation and
internal whitespace still must match. Patches try exact context, normal fuzz
(up to two surrounding context lines), then flexible whitespace. Failed
attempts are discarded before retrying.

Review completion validates every original before writing anything, then
applies the accepted snapshots together and rolls back on write failure.
Files changed on disk or with unsaved visiting buffers block completion and
leave the queue available for cancellation or retry. Unmodified visiting
buffers refresh after acceptance. Killing the conversation discards its queue;
hiding or killing only the review list does not discard proposals.

*** Background commands

=Bash= normally waits for a command to finish. Prefer this foreground mode
for tests, builds and commands whose result is needed before proceeding.
Set =background= to =true= for servers, watchers or jobs the agent can work
alongside. It immediately returns a =process_id=,
leaving the agent free to run other commands and inspect output later:

#+begin_src json
{"command":"npm run start","query":"Report the server URL or startup errors","background":true}
#+end_src

The =Process= tool manages these jobs using the returned ID:

#+begin_src json
{"action":"list"}
{"action":"read","process_id":"bash-1"}
{"action":"read","process_id":"bash-1","view":"tail","max_chars":8000}
{"action":"wait","process_id":"bash-1","until":"exit","timeout_ms":30000}
{"action":"send","process_id":"bash-1","input":"yes\n"}
{"action":"interrupt","process_id":"bash-1"}
{"action":"kill","process_id":"bash-1"}
{"action":"remove","process_id":"bash-1"}
#+end_src

=list= shows running and completed background jobs, their commands, working
directories and status. =read= returns available stdout and stderr immediately,
consuming unread output by default. Optional =offset= replays from an absolute
character position without changing the unread cursor; =max_chars= limits a
read to 1–20000 characters (default 12000). Results include =next_offset= and
=output_end=. The unread cursor is shared by the chat and its sub-agents.
Set =view= to =tail= to read the latest characters directly without changing
that cursor. Omit =offset= entirely for tail, including =offset=0=. Results
also include =retained_start= and =output_start= and distinguish discarded output from
earlier retained output omitted by the tail view. Use an explicit =offset=
to inspect that earlier output if needed.

=wait= with =until=exit= (the default and only supported condition) waits
asynchronously for termination or a deadline, keeping Emacs responsive.
Progress output does not end the wait. =timeout_ms= defaults to 30000 and
accepts 0–60000; zero returns an immediate snapshot. Results include
=wait_reason= (=exit= or =timeout=), process status, exit code or signal when
finished, and output. Timeout does not stop the job. Wait defaults to
=view=tail=, or =unread= when =offset= is supplied; =max_chars= and explicit
=view= work as for read. Use wait instead of repeated reads when completion
is needed. Servers and watchers may never exit, so use read to inspect them.
Removing a completed job resolves any pending waits with =wait_reason=removed=.
Cancelling a request or killing its calling buffer cancels its waits without
stopping jobs owned by a surviving conversation.
Invalid arguments return a tool error so the agent can correct the call
without aborting the request or stopping the job.

Each job retains the most recent =gptel-agent-process-output-limit= characters
(default 200000). Older output is discarded and a read reports any missing
range. Redirect output to a file in the command if you need a complete durable
log. Completed jobs retain their status and output until =remove= or chat
cleanup. Foreground Bash keeps a bounded prefix in memory and spills oversized
output to a temporary file as it arrives. Its complete log remains available
through the result-explorer handoff after completion.

Foreground commands belong to their calling buffer and request. Cancelling the
request or killing that buffer stops their process groups and removes unfinished
logs. Background jobs retain the separate lifecycle described below.

Jobs belong to the originating conversation buffer, including jobs started by
its sub-agents. They survive later turns, request cancellation and sub-agent
completion. Another chat cannot look up or control them through =Process=.
Killing the conversation buffer kills its running jobs and releases their
output; jobs are not restored after an Emacs restart. This ownership is a tool
management boundary, not an OS sandbox: Bash still has normal shell access.

Use =interrupt= for SIGINT, then =kill= for SIGKILL if needed; both target the
job's process group, including ordinary child processes. Keep commands in the
foreground of the managed shell: do not append =&=, use =nohup= or daemonize.
Detached descendants are outside this lifecycle. Input uses pipes, so terminal
UI programs and shell job control are not supported. Some programs buffer
output when connected to a pipe. Remote process support depends on the Emacs
file handler. Sending input follows normal tool confirmation; reading,
listing and stopping owned jobs need no tool-specific confirmation.

The default agent includes =Process=. Custom agents using
background Bash should add =Process= to their tools as well.

*** What is an "agent"?

"Agent" is the (now common) parlance used to refer to a bundle of configuration,
consisting of

- a system prompt (instructions),
- tools (functions the LLM can call)
- and the harness used to run or call the LLM.

gptel uses the term "preset" for such configurations.  A preset can specify the above and any other behavior, such as the model used, API call parameters and so on.

=gptel-agent= is implemented as a preset for gptel and can be modified/extended easily.

*** Messages between main chats

When the user explicitly asks to find or message another main agent/chat,
load =Skill(main-chat-messages)=. This enables the separate =MainChat= tool
in the current turn; custom presets can also include it directly.

| Action | Behavior |
|--------+----------|
| =list= | List other live main gptel buffers: stable =chat_id=, buffer name, directory and pending-message count |
| =send= | Queue =message= for an exact =chat_id= from the list |

Discovery returns at most 20 entries per page; pass =next_offset= as =offset=
to continue. It never reads transcripts. Generated discussions, workers and
review asides cannot use this tool or appear as recipients, including closed
or detached discussions. =DiscussionControl= still sees only the calling
conversation's own discussions. Main-chat IDs survive buffer renames, are
not reused after killing a buffer, and last only for this Emacs session.

A recipient receives messages at its next model-request boundary, after any
pending tool results. Sending never starts a new model request, submits an
unsent draft, or automatically replies. Idle, aborted and failed chats keep
messages until their next user-started turn. Read-only recipients keep messages
queued until a request boundary with a writable buffer. Messages are labeled as peer
context, not user instructions or authorization; ordinary replies stay local.
The recipient need not enable =MainChat= to receive messages, but its request
must run =gptel-agent-chat--localize= (installed in the default prompt transforms).

The tool and skill instruct the model to list/send only on explicit user
requests, never for routine collaboration or automatic acknowledgements.
This is a model instruction, not a natural-language authorization detector.
Normal gptel confirmation settings apply: skill activation pre-approves the
tool in =auto= mode; always-confirm mode and per-call hooks still take precedence.
Enabling the tool on one turn does not authorize unsolicited later sends.

Messages have no character limit and are delivered without truncation.
=gptel-agent-chat-inbox-limit= defaults to 16 pending messages per recipient.
Full inboxes reject new messages without discarding earlier messages.
Inboxes live only in their buffers and disappear when those buffers
are killed. There are no polling timers, background jobs, global transcript
copies or automatic wakeups; buffer discovery runs only on explicit tool calls.

*** Managed discussions

The default =gptel-agent= preset discovers discussion management through the
bundled =skills/managed-discussions/SKILL.md= skill. The package's =skills/=
directory is a discovery fallback even when =gptel-agent-skill-dirs= is
customized; user and project skills retain precedence. Calling =Skill= loads
the workflow instructions and adds =Discussion= and =DiscussionControl=
to the current tools in the same turn. Existing tools remain available on later
turns. Custom presets can still list both tools explicitly.

=Discussion= creates a separate, ordinary gptel buffer with a title and opening
prompt. It inherits the creating request's model, backend, system prompt, active
tools (including tools activated by skills) and confirmation settings; an
optional existing =preset= can override them.
It starts without the parent's transcript or attached context. An optional
=directory= selects its working directory, including another project; relative
paths resolve against the creating chat's directory. Skill instructions and pre-approvals
belong to each conversation separately; inherited tools use their original
confirmation settings. A child loads skills for their instructions and its own
pre-approvals. Approving discussion management does not approve child tool calls.

Omitting =preset= (or passing an empty string) copies the current request's
settings, including local changes; it does not reapply the parent's saved
preset. An explicit preset is applied on top: settings it specifies override
inherited values, while unspecified settings remain inherited. A preset's tool
list replaces the inherited tools, and the child also receives =DiscussionReport=
to communicate with its parent. Preset parents, composition forms, and
=:pre=/=:post= hooks are honored.

The =Discussion= tool advertises the names and descriptions of all presets
registered with =gptel-make-preset=, including user-defined presets outside
gptel-agent. This selection is independent of the =Agent= tool's sub-agent
allowlist. The discussion instructions tell the model to choose a preset suited
to the child's task even when the user has not named one. When a read-only
=gptel-plan= or =ask= conversation is asked to start an implementation discussion,
it loads =managed-discussions= and directly selects an implementation-capable
preset, using =gptel-agent= when available unless another preset fits better.
An explicit user choice takes precedence. Inheritance is appropriate when the
parent's role already suits the task or the user explicitly requests it.
For example, a planning conversation can hand off implementation with:

#+begin_src json
{"title": "Implement the feature", "prompt": "Implement this self-contained plan: ...", "preset": "gptel-agent"}
#+end_src

The child uses =gptel-agent='s system prompt and tools; the parent remains a
planning conversation. Pass your own registered preset name in the same way.
Unknown names return an error without creating a discussion.

Pass =worktree: true= to start the discussion in a new Git worktree. The tool
instructs models to use this option only when the user explicitly requests a Git
worktree or isolated Git workspace; ordinary coding or delegation requests
keep the existing directory by default.

#+begin_src json
{"title": "Implement in isolation", "prompt": "Implement the feature and report the changes.", "worktree": true}
#+end_src

The source is =directory= when supplied, or the calling chat's current
directory otherwise. Relative paths resolve against the caller. A repository
subdirectory or an existing worktree is accepted. The source must belong to a
Git working repository with at least one commit; invalid sources return an
error without starting a discussion.

The new checkout is a randomly named sibling of the source repository root,
such as =/projects/app-discussion-aB12cD/=, on a new branch such as
=gptel-discussion/aB12cD=. It starts at the source's current =HEAD= commit;
uncommitted and untracked files are not copied. The child starts at the new
worktree root and discovers project instructions there. Omitting =worktree=
or passing =false= keeps the ordinary directory behavior.

The creation result and =DiscussionControl list/read= include the working
directory, worktree path, branch at creation, source repository and directory,
and starting commit. These details are also included in the child's opening
context. Closing either conversation retains the worktree and branch for
review, merging and later cleanup. If child startup fails after checkout,
the failed discussion retains these details so the workspace stays inspectable.

When the work is finished and integrated, the managing agent can remove the
generated worktree with =DiscussionControl cleanup=. The branch is kept by
default; add =delete_branch: true= to attempt its deletion too:

#+begin_src json
{"action": "cleanup", "discussion_id": "discussion-1", "delete_branch": true}
#+end_src

Cleanup accepts an idle, failed, cancelled or closed discussion owned by the
calling conversation. It closes monitoring, retains the editable transcript,
and resets that buffer's directory to the source repository. Active or queued
work, other discussions sharing the directory, managed background processes,
unsaved file buffers and pending file reviews must be resolved first. Git
refuses dirty or locked worktrees; a switched branch or detached HEAD also
requires inspection. Cleanup never forces removal or branch deletion.

Branch deletion uses =git branch -d= and applies only to the branch created for
this discussion. If Git refuses deletion (for example, because the branch is
unmerged), the worktree remains removed and the branch is retained. The result
reports both states, also visible in =list/read=; retry =cleanup= after
integration to delete the branch. Repeated successful cleanup calls are safe.

**** Skill tool declarations

=allowed-tools= follows the experimental [[https://agentskills.io/specification#allowed-tools-field][Agent Skills specification]]: a
space-separated string of pre-approved tool names. gptel-agent supports exact,
uniquely registered names only. Category grants, wildcards and scoped expressions
such as =Bash(git:*)= are unsupported. If any declaration is invalid, missing or
ambiguous, =Skill= returns the instructions with a diagnostic and adds none of
that skill's tools or pre-approvals. Tools must already be registered with gptel;
skills do not install Lisp implementations.

gptel-agent also exposes those tools to the current request and its provider
schema. This is host behavior, not a requirement of the standard. Activation
persists in the conversation across turns, with fresh request-owned dispatchers;
repeated loading is idempotent. In =gptel-confirm-tool-calls= auto mode the tools
are pre-approved. Always-confirm mode and per-call confirmation/blocking hooks
keep their normal precedence. Global settings and registered tools are unchanged.

Discovery exposes only name and description. Skills without =allowed-tools=
continue to load instructions only. Skill frontmatter is data, not evaluated
agent configuration: agent-definition =pre= and =post= evaluation and hooks
remain unchanged. Automatic unloading and persistence across Emacs restarts are
not supported.

**** Discussion lifecycle

Discussions run independently and survive the parent's completed turn. Ordinary
answers stay in the child, including replies to direct user messages. Questions,
approvals, failures and file-review notices also stay there. Finishing a child
turn or raising an alert does not start another request in the parent.

Each managed child receives =DiscussionReport=, including with a custom preset
or when its parent enabled management through a skill. The child chooses when
to send a concise answer, useful update or blocker to its managing conversation.
It should report when the parent asks for an answer, without routinely forwarding
direct user exchanges or acknowledgements. The parent can use =send= to request
a report, or =read= to inspect the child's work without a child model request.

Only explicit reports reach the parent at its next safe request boundary, or
start a new ordinary gptel turn when it is idle. They are recorded in the parent's
visible transcript. These turns use the parent's configured model and incur
normal API usage. Reports go only to the child's immediate managing conversation.

| Tool / action | Purpose |
|---------------+---------|
| =Discussion= | Start a fresh chat; return its stable =discussion_id= immediately |
| =DiscussionReport= (child only) | Explicitly send a chosen message to the managing conversation |
| =DiscussionControl list= | List discussions owned by this conversation |
| =read= | Read status, pending interactions and a page of the editable transcript |
| =send= | Steer running work, or start a follow-up in the same chat |
| =wait= | Receive an explicit report for selected =discussion_ids=, up to 60 seconds; also shows already pending interactions |
| =answer= | Answer a pending =AskUserQuestion= using its exact =request_id= |
| =close= | Abort current work and end monitoring; keep the editable transcript |
| =cleanup= | Remove a finished discussion's generated worktree; optionally delete its branch with =delete_branch: true= |

=read= does not consume report delivery. Its =offset= is a zero-based character
offset; =next_offset= identifies the next page. Reports and transcript
pages are bounded by =gptel-agent-discussion-report-limit= (16000 characters by
default). Ownership lasts across turns, but a different conversation cannot
manage these IDs.
Completing a turn without reporting does not satisfy =wait=; it can time out.

Run =M-x gptel-agent-discussions= in the parent or a managed discussion to open
the list. =RET= opens a chat, =s= sends a message, =c= closes monitoring, and =g=
refreshes. In a child buffer, use =gptel-send= normally for a new turn. During an
active turn, use =M-x gptel-agent-discussion-send= to queue steering; it is
delivered after pending tools finish, or as a follow-up if the response finishes
first. Concurrent requests in the same monitored buffer are prevented.

The parent can answer structured questions itself. Tool approvals stay in the
child discussion buffer, where the user can approve or reject them with gptel's
confirmation controls. An echo-area notice identifies the buffer waiting for
approval; no approval panel is copied into the managing conversation, and it
cannot reject the child's tool calls. Stale callbacks cannot execute the same
tool or answer twice. Tool approvals and questions raised by a discussion's
sub-agents remain accessible in that discussion's buffer; =Cancel request=
stops the particular request awaiting approval.
=read= exposes pending interactions, failures and outstanding file reviews when
the parent asks for them. File reviews retain the configured applied/staged
review behavior and the child's existing review queue.

Automatic sending waits when you have an unsent draft. Send that draft with
=gptel-send= to include queued events, or discard it and run
=M-x gptel-agent-discussion-resume=. Aborting or failing a parent request pauses
automatic delivery without stopping its discussions. A new manual send or
=gptel-agent-discussion-resume= re-enables delivery. Killing the parent detaches
its discussions, which remain usable; killing a child marks it closed without
waking the parent. =close= retains the transcript and stops only that discussion's
current request (including its ordinary Agent workers).

Management IDs, ownership and event queues are retained for the current Emacs
session; saving and reopening a transcript does not restore supervision.
After updating, reload/rebuild the package and run =gptel-agent-update=, then
reapply the =gptel-agent= preset. For custom presets, include both =Discussion=
and =DiscussionControl= in their tool lists.

*** Using sub-agents

gptel-agent can delegate tasks to "sub-agents".  Sub-agents can be specified in
Markdown or Org files in a directory.  To see how to specify agents, examine the
"agents" directory in this package (or see below).  You can add your directory
of agents to =gptel-agent-dirs=, which see.

The following sub-agents are bundled:
- =researcher= is read-only and can search the web or through local files for
  information.
- =introspector= can examine the state of Emacs, and access or search
  documentation from your live Emacs session.
- =result-explorer= extracts evidence from oversized saved tool results.

Each parent's definition controls its sub-agents through an =agents= list.
The default =gptel-agent= and the read-only =gptel-plan= and =ask= definitions
offer =researcher= and =result-explorer=.  The default agent handles
implementation and verification directly.
Worker availability has no package-level exclusion list.
The interactive =gptel-agent=, =gptel-plan= and
=ask= presets are main agents, never sub-agents; an agent also cannot delegate
to itself.  These guards apply even if those names appear in an =agents= list.
Add custom sub-agent names to the parent's =agents= list to
make them available there, then run =M-x gptel-agent-update= in the chat to
refresh it.  Activating or reapplying a main preset also refreshes its
sub-agent definitions.  Selecting a preset through gptel's menu enforces
the same =agents= list as starting a dedicated agent session.

Use =M-x gptel-agent-toggle-agent= to narrow the current conversation's
selection; choosing none disables delegation.  This does not affect other
chats or expand the parent's allowed list.  Requests already in flight retain
their original selection.

The LLM should automatically delegate tasks to enabled agents as required, but
you can also explicitly request delegation: "/Use the researcher to find out
if.../" or "/Use my-custom-agent to.../".

The =Agent= tool returns an =agent_id= with each completed task.  The main
agent can pass it to =Agent= again, with the same =subagent_type= and a new
=description= and =prompt=, to request a related follow-up or correction.
The sub-agent keeps its original configuration, conversation and full tool
results, including evidence shortened in the inspection buffer.  Each follow-up
gets fresh timeout, round, retry and tool budgets.  The =agent_id= argument is
optional; omitting it or passing a blank string starts a separate conversation.
IDs belong to the calling chat; a running agent cannot receive another task
until it finishes, but can receive steering for its current task. Failed or cancelled requests
remain diagnostic-only and cannot be resumed.

Set =background: true= on =Agent= (including follow-ups) to receive an
=agent_id=, invocation-specific =run_id= and status immediately. Omitting it,
or passing false, preserves the blocking call. Configuration, evidence, scope
restrictions and supervision limits apply in both modes.

=AgentControl= operates on the calling parent's workers:

| action | arguments | behavior |
|--------+-----------+----------|
| list   |           | Concise statuses of owned workers |
| read   | agent_id  | Current status and latest completed invocation; does not consume delivery |
| wait   | agent_ids (optional) | Wait for a new terminal outcome from any selected worker |
| send   | agent_id, message | Queue a correction for the active task without resetting its budgets |
| cancel | agent_id  | Cancel that worker and all its descendants |

Results arrive automatically at the next safe model-request boundary, after
any outstanding tool results. Explicit waits consume the same completion
queue, return immediately for queued results, and report =no_eligible_work=
when there is nothing to await. There is no polling or repeated model request
while waiting. Use =Agent= with =agent_id= for a completed worker's next task;
=send= only steers work that is still active.

The harness keeps the parent turn open until every descendant is terminal and
its outcomes have reached its parent. An early final answer is interim output:
the chat shows =Waiting for agents=, retains its request history, and inserts
no next-user prompt or =Ready= status. A completion resumes the same request
for synthesis, even while other workers are running. The same gate applies to
nested workers and to accepted steering queued near completion. Workers waiting
for tools, permissions, retries or descendants remain active; task timeouts
continue to apply. Aborting or closing a chat cancels its worker subtree and
pending wakeups. Unrecoverable parent failures also stop descendants.

Worker orchestration is owned by the creating chat; workers can use separate
working directories through =directory=. It does not
add peer messaging, shared scheduling, worktree isolation or persistence across
Emacs restarts. Background shell jobs keep their separate existing lifecycle.

Completed sub-agent buffers stay available for follow-ups until you close them
or their parent chat.  Closing the parent chat cancels active sub-agent requests
and closes all its sub-agent buffers, including nested agents and retained
failure transcripts.  A =result-explorer= follow-up must retain its original
=result_file= and =query= scope.

#+html: <details><summary>
**** Why?
#+html: </summary>

LLMs often run into dead-ends when trying things, and this can both bloat and
pollute the context window.  Sub-agents don't share any context with the main
session and return relatively concise reports that gptel-agent can refer to.

Sub-agents can be provided with tools specific to their task, which improves the
quality of the result.  They can also be restricted accordingly by, for example,
providing read-only access to resources.

Sub-agents can be configured to use specific models or other API parameters
(like the level of reasoning) independent of gptel-agent.  They are essentially
gptel presets.

Each delegation snapshots its backend, model, streaming mode, system prompt,
tools and request parameters.  Tasks are unlimited by default.  Add
=task-timeout= and/or =max-request-rounds= to an agent's frontmatter or Org
properties to bound that agent; =nil= or =false= explicitly means unlimited.
The built-in researcher uses a 3600 second timeout and 100 model request rounds;
the result explorer uses 1800 seconds and 60 rounds.  The introspector is
unlimited.  The global fallback options are
=gptel-agent-task-timeout= and =gptel-agent-max-request-rounds=; an omitted
per-agent value inherits its global fallback, and both fallbacks default to nil.
Transient transport retries remain bounded by
=gptel-agent-max-request-retries= and =gptel-agent-retry-delay=.  Authentication
and malformed-request errors are not retried.

=gptel-agent-preset= may be a named gptel preset or a preset plist and can be
set globally or buffer-locally on the parent request buffer.  Child request
configuration is applied in this order: inherited parent settings, harness
defaults, =gptel-agent-preset=, then per-agent frontmatter.  Thus unspecified
parent settings are retained, the shared preset configures all sub-agents, and
explicit per-agent settings take final precedence.  Preset parents, composition
forms, and =:pre=/=:post= hooks are honored at each layer.

The Agent task overlay includes an =[Inspect sub-agent]= action.  Its buffer
shows the prompt, model rounds, streamed output, tool arguments and results,
retries, and terminal reason.  Failed, timed-out and cancelled runs keep this
buffer by default; set
=gptel-agent-keep-failed-run-buffers= to nil to clean them up immediately.
Repetition detection compares the tool name and all argument values exactly;
JSON object field order is ignored.  Changing a depth, line range, query or
other parameter therefore counts as a different call.  The existing
=gptel-agent-max-similar-tool-calls= setting now limits identical read/search
calls in recent history, including non-consecutive repeats.  Repeated calls
and exact alternating cycles are skipped once so the model can change
strategy.  At =gptel-agent-max-loop-violations= the same sub-agent enters a
tool-free finalization turn: it keeps its complete tool transcript and system
prompt, interprets the evidence it gathered, and returns the final answer
itself.  Web-heavy sub-agents have a separate
=gptel-agent-max-web-tool-calls= budget, defaulting to 50 calls; exceeding it
triggers the same synthesis turn instead of returning raw tool results to the parent.  Round
limits reserve this finalization turn, then return an explicit inconclusive
report only if the model still produces no usable answer.  Web searches default to
=gptel-agent-web-search-default-count= results and are capped by
=gptel-agent-web-search-max-count=.

=WebFetch= handles HTML and common textual content types directly.  HTML uses
readability extraction with full-page and decoded-body fallbacks; binary or
client-rendered resources return an explicit limitation.  Responses default to
=gptel-agent-web-fetch-max-chars= characters and request timeout is controlled
by =gptel-agent-web-request-timeout=.  The tool's optional =max_chars= argument
can raise the per-call output size for a known large textual resource.  YouTube
URLs use this same tool and return the video description and transcript; there
is no separate YouTube tool.

=Bash= calls include a =query= stating what should be extracted from their
output.  Results larger than =gptel-agent-tool-result-max-chars= are saved in
full under the temporary directory and replaced by a bounded preview.  The
notice supplies an exact =result_file=/=query= contract for the built-in
=result-explorer= sub-agent.  Its pathless read/search tools are locked by the
harness to that registered file, and its report cites file line evidence that
the parent agent can verify with =Read=.  Preview size is controlled by
=gptel-agent-tool-result-preview-chars= and
=gptel-agent-tool-result-preview-lines=.

=Glob= and =Grep= run asynchronously. Directory enumeration and metadata reads
use an isolated Python 3 subprocess when available, otherwise a clean batch
Emacs subprocess. =Grep= prefers =rg=, then =grep -E=, then a separate batch
Emacs process. Its request-local description and =regex= schema advertise the
selected native dialect, like =ResultGrep=; an in-flight query never switches
dialects. Backend changes are advertised before the next model request.

Glob retains its case-insensitive Emacs basename wildcard syntax, typed
symlinks, depth handling, and newest-first ordering. Both directory tools
include hidden, ignored, dependency and build entries, exclude only =.git=
directories, and do not traverse directory symlinks. Grep's =glob= uses the
same basename matching as Glob. Grep is case-sensitive and returns quoted
absolute filenames with line numbers. Searches currently require local paths;
remote paths fail explicitly instead of running blocking TRAMP operations.

Each call has a =gptel-agent-search-timeout= deadline (30 seconds), including
traversal, and stops when its request is aborted or its owning buffer is killed.
=gptel-agent-search-max-entries= bounds examined directory entries (20,000),
=gptel-agent-search-traversal-max-bytes= bounds candidate metadata (4 MiB), and
=gptel-agent-search-max-results= caps Glob entries or Grep matching lines
globally (1,000). Both tools accept =max_entries= and =max_results= to lower
these ceilings, plus =depth= to restrict traversal. Grep accepts 0–15 context
lines; a limit can cut trailing context short. Output stops at
=gptel-agent-tool-result-max-chars=; individual subprocess records are bounded
to 64 KiB and error diagnostics to 2,048 characters. The Emacs grep fallback
skips lines over 64 KiB and reports incomplete coverage.

Limits and failures return explicit =incomplete= coverage with any collected
results. Partial Glob results are sorted only within the collected subset,
not necessarily the newest entries in the whole tree. No unbounded full result
is saved. Narrow the directory, pattern or depth, or explicitly increase the
configured ceiling before retrying. A zero-match response is conclusive only
when coverage is =complete=.

=ResultGrep= selects =rg= first, otherwise =grep -E=, otherwise a built-in
Emacs reader. Its request-local description *and* =regex= argument schema name
the selected backend and its native regexp dialect before the model writes a
query. Ripgrep uses its default Rust regex engine with Unicode enabled (no
PCRE2); =grep -E= uses extended regular expressions in the C locale; the
fallback uses Emacs regular expressions and its standard case table. There is
no regex translation. For example, alternation is =ERROR|WARN= with the two
external backends and =ERROR\|WARN= with Emacs. Case-insensitive matching follows
the advertised engine, including Unicode folding for ripgrep/Emacs and ASCII
folding for grep. All backends search individual lines and report nonempty,
non-overlapping matches. Patterns are limited to 4096 UTF-8 bytes and cannot
contain literal newline or NUL characters.

The selected executable is captured with that request's schema. If it becomes
unavailable, the tool reports that failure without trying another dialect.
Backend selection and both the schema and dispatcher refresh before the next
model request, including subsequent tool rounds. Other in-flight requests keep
their own contracts.

Search runs asynchronously, retains at most 100 numeric match records, an
8 KiB external output record and 2 KiB of diagnostics, and caps rendered evidence
at =gptel-agent-tool-result-preview-chars= (plus a short coverage notice).
Subprocess chunks are discarded as they arrive; oversized match records stop
collection with an incomplete result. Narrow a regexp such as =.*= if it emits
an enormous match. External engines manage their own internal memory; these
limits bound Emacs's retained data, not the executable's allocations.

The Emacs fallback reads 64 KiB per timer slice and joins chunk boundaries
within a line. It retains at most 64 KiB of line bytes and skips larger lines,
including their entire remainder, without allocating them. Such results always
report incomplete coverage and identify the first skipped line/byte offset;
use =ResultRead= to inspect it. Search has a 30-second deadline, including
evidence extraction. Match limits, output limits, failures, file changes and
timeouts are reported separately from completion; a partial scan never claims
a complete absence of matches. Cancelling the owning request or killing its
buffer disposes processes/timers without delivering obsolete results.

Evidence uses exact one-based line and *UTF-8 byte* columns (tabs occupy one
byte), with a zero-based match byte offset and the excerpt's starting column.
Pass =next_start_byte= back as =start_byte= to continue a limited search.
Skipped oversized fallback lines remain uncovered even if later matches are
reported; the continuation does not silently advance past that gap.

=Read= and =ResultRead= also read UTF-8 in bounded 64 KiB chunks. The
=gptel-agent-read-file-size-threshold= limit (400 KiB by default) now bounds
ranged =Read= output as well as whole-file reads, including open-ended ranges
and single enormous lines. =ResultRead= retains at most the preview budget in
input bytes and returns at most that many excerpt characters, plus its notice;
its existing maximum of 200 lines still applies. A limited read reports
=start_line= and =start_column= for continuation; columns are one-based UTF-8
bytes, and generated continuations never split a character. Staged-file reads
obey the same output limit without copying the entire staged text into a new
buffer. Selecting late lines still requires scanning preceding bytes, in
bounded chunks. These readers do not auto-detect other text encodings.

Foreground Bash enforces this limit while output arrives, rather than waiting
for the command to exit. It retains at most the larger of the result and preview
character limits (20000 characters with the defaults), plus the current incoming
chunk, with undo disabled. Oversized output is appended to disk and is never
read back in full to construct the response. Small commands need no log file.
Saved Bash logs contain the decoded stdout and stderr; a failed command's exit
status appears in the tool response. Completed oversized logs remain in the
temporary directory for inspection and consume disk space proportional to their
output. A log write failure stops the command and returns a tool error.

**** Agents from Markdown files
#+html: </summary>

gptel-agent reads agent specs from files in =gptel-agent-dirs=, which you can
customize.

You can specify the agent name, description and tools used as YAML front-matter
in a Markdown file, followed by the system prompt:

#+begin_src markdown
---
name: arxiv-explorer
description: Searches ArXiv and parses results
tools: [mcp-arxiv, WebSearch]
task-timeout: 1200
max-request-rounds: 30
pre: (lambda () (gptel-mcp-connect '(arxiv) 'sync))
---

You are a specialized research agent with access to ArXiv.  Your purpose is to
search for and gather information efficiently.

<core_responsibilites> ...  </core_responsibilities>

...
#+end_src

=name= defaults to the file name, so only the =description= is mandatory.
=tools= is a list of tool names or categories.  The optional =task-timeout= and
=max-request-rounds= keys set this agent's supervision limits; leave them out
to inherit the global defaults, which are unlimited.

For an agent with the =Agent= tool, =agents= lists the sub-agent names it may
call, for example =agents: [researcher, result-explorer]=.  An empty list
(=agents: []=) disables delegation.  Omitting the field allows all discovered
sub-agents except the caller itself; main presets are always excluded.
A delegated agent may further restrict its
selection through its own definition; it cannot expand the inherited list.
In Org definitions, use a space-separated property such as
=:agents: researcher result-explorer=, or an empty =:agents:= property for none.

You can specify any other keys that gptel recognizes as preset keys, including a
specific model, backend and API parameters.  See =gptel-make-preset= for
details.

In the above example, the =:pre= key is an elisp function that runs before the
agent is called.  I am assuming a tool category named "mcp-arxiv" is provided by
the "arxiv" MCP server.

** File tool path contracts

File tools use filesystem types, never filename extensions. A directory can be
named =Poulet.java=; a file can have no extension. Use =PathInfo(path)= to inspect
an exact on-disk target, or =Glob(pattern, root_directory, depth, type)= with
=type=all= to list typed entries. Glob includes hidden entries, omits =.git=
directories, and does not traverse directory symlinks.

- =Write(file_path, content)= creates or overwrites a complete file, automatically
  creating missing parent directories. File paths must not end in =/=.
- =Insert(file_path, line_number, new_str)= adds text to an existing file.
- =Edit= requires =mode=replace=, =mode=patch=, or =mode=batch=. Replacement uses
  =file_path= and a nonempty =old_str=. A patch explicitly selects either
  =file_path= for one existing file or =root_directory= for relative diff headers.
  A batch uses =root_directory= and ordered =operations= with relative
  =file_path= targets (or =root_directory= for a directory patch).
- =Mkdir(directory_path)= creates a directory and all missing ancestors. It is
  unnecessary before file creation with Write or Edit.
- =Rmdir(directory_path)= removes exactly one empty directory, refusing symlinks,
  nonempty directories, and the working directory or its ancestors.

For example, create a Java file directly:
#+begin_src json
{"file_path":"/project/src/Poulet.java","content":"class Poulet {}"}
#+end_src
If that target already exists as an accidental directory, inspect it with
PathInfo and Glob, use Rmdir only if it is empty, then Write the file.

These contracts replace the former =path=/=filename= Write arguments,
=parent=/=name= Mkdir arguments and inferred Edit modes. Reapply agent presets
after loading the updated tools so sessions receive the new schemas.
