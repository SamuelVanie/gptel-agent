* Embedding agents in workflow hosts

Workflow packages can use agent tools in their own =gptel-request= calls
without advising internal worker functions. Configure the request buffer's
preset and pass its =gptel-prompt-transform-functions= to =gptel-request= so
agent tools receive their request-local dispatchers.

Use =(gptel-agent-session-buffer-record BUFFER)= to include a chat in a
workflow checkpoint. Pass that record to
=(gptel-agent-session-buffer-from-record RECORD)= to reopen an editable
chat with the original conversation, response and tool boundaries, draft,
model and settings. For a standalone local file, use
=(gptel-agent-session-export-buffer BUFFER FILE)= and
=(gptel-agent-session-import-buffer FILE)=. A host that already holds a
record can save it with =(gptel-agent-session-write-record RECORD FILE)=,
even after the chat closes. Imports return an undisplayed buffer with a
fresh identity by default. Both forms work with session autosaving disabled.
When the host owns persistence, pass =t= as the optional =EXTERNAL= argument
to =gptel-agent-session-buffer-from-record= or =gptel-agent-session-import-buffer=.
The host can then reopen the conversation with its own run history.

In a new host-owned chat, set =gptel-agent-session-managed-externally=
buffer-locally before enabling =gptel-mode=. The global agent session catalog
excludes the chat and its descendants even when session autosaving is enabled
later. To retain nested transcripts, install a function on
=gptel-agent-child-buffer-functions=. It receives the parent buffer, new child
buffer, and child kind (=agent= or =discussion=) before the first request.

Before starting a host-owned invocation, call =gptel-agent-supervise= with
its buffer. The returned opaque handle covers its agent workers, managed
discussions, nested descendants and queued discussion follow-ups. Only
supervised requests wait for discussion turns to settle. Ordinary interactive
chats keep their independent discussion behavior. A silent child completion
releases the held answer; an explicit =DiscussionReport= resumes the same
request for synthesis. Sub-agent callbacks accept raw injected reports as
transcript content without including them in the final result.

| Public function | Purpose |
|-----------------+---------|
| =gptel-agent-supervise= | Establish buffer ownership before starting requests; accepts =:on-state-change= and =:on-tool-approval= callbacks |
| =gptel-agent-supervision-request-live-p= | Check whether a retained request still belongs to the active handle and can advance |
| =gptel-agent-supervision-allow-outside-reads= | Attach the initializing root request to its handle and allow local outside reads during supervision |
| =gptel-agent-supervision-retry= | Rearm a failed root request's completion gate before the host resumes that same FSM |
| =gptel-agent-supervision-stop= | Idempotently release supervision and cancel descendants while retaining inspection buffers |

The state callback receives =(handle fsm event)=, where =event= is
=waiting-discussions= or =changed=. Notifications can repeat. The approval
callback receives =(handle fsm calls)= with gptel's live tool/callback entries;
return non-nil to handle the approval, or nil to keep native display. Before
accepting saved calls, check =gptel-agent-supervision-request-live-p=, that the
FSM still awaits tools, and that its request info is the same object that
produced the approval. Approval callbacks and handles must never be persisted.
Question forms and separate file-review interfaces retain their existing UI.

The host owns the root transport, terminal handlers, retry policy and request
budget. Stop supervision when an invocation ends, and abort the root transport
when cancelling it. Start a fresh handle for a new invocation or feedback
request. Child model calls remain internal to the host's invocation. Lifecycle
notifications schedule deferred settlement; supervision never polls a model
or runs a repeating timer.
